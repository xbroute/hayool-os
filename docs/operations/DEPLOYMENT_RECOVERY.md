# Deployment, installation, upgrades and recovery

ADR-025/026. One release manifest and codebase for Cloud, Dedicated and On-Prem; infrastructure configuration differs. Separate dev/staging/prod DBs, objects, keys and identities; current VPS is not silently production. Ubuntu LTS + container/Compose initial target, exact supported release freeze before bootstrap. No production ports for DB/cache/workflow/vault admin.

Installer CLI plus safe authenticated setup wizard: CPU/RAM/disk/domain/TLS/version/DB/cache/blob/workflow/mail/license/key/backup checks -> durable install ID -> create service identities -> migrations -> first tenant/admin MFA -> provider sandbox/AI-off defaults -> backup -> smoke -> completion evidence. Retry resumes phases without duplicate admin/entity. Temporary setup token expires; setup endpoint locks after completion. No secrets embedded in shell history or exported diagnostic bundle.

Upgrade preflight: signed artifact/digest/SBOM/license -> deployment/pack compatibility -> backup plus recovery point -> additive migration -> compatible app -> throttled resumable backfill -> verify -> cutover -> later approved destructive cleanup. Maintain N/N-1 application-schema compatibility across rollout window. Rollback code only where schema/data contract supports; otherwise forward-fix. Never restore old DB to undo already accepted payments without reconciliation and explicit recovery plan.

Cloud tenants use shared infrastructure with tested isolation; dedicated isolates runtime/data/keys. On-Prem supports external AI/network/telemetry off, signed offline license/update/package import and documented manual provider operation. Network bridge outbound-only approved projections; no central direct DB. License expiry uses defined grace/read-only/export path, never destructive lockout. Remote support requires expiring authorized grant and audit.

Backups cover DB/PITR, object versions, config/pack registry, audit, workflow state and secure key-recovery references. Encrypted off-host copy in eligible region/failure domain. Candidate managed objectives RPO<=15min/RTO<=4h; validate actual data volume and recovery keys. Recovery: isolate target -> restore compatible DB/object/workflow point -> keys/config -> replay deletion tombstones -> reconcile external effects/outbox -> verify balances/tenant ACL/files -> smoke -> authorized reopen. Prove actual measured loss/time; backup job success alone fails gate.

Telemetry: structured redacted logs, metrics/traces with correlation across API/workflow/provider/event/financial outcome. Monitor auth denial, tenant anomalies, transaction errors, queue lag, stale projections, dead-letter, DB saturation, storage/backup age, provider eligibility/health, AI spend and support SLA. The independently testable V1.0 health/telemetry obligation is REQ-PLAT-018 and `OPERATIONAL_HEALTH_TELEMETRY_CONTRACT.md`. Debug log != authoritative audit. On-Prem telemetry opt-out does not disable local diagnostics. Incident runbooks named roles, contact/escalation and customer communication are required before live service.

Canary candidate: 5% -> 25% -> 100% only for compatible deployment and approved cohort; min 30min each observed stage for initial policy. Rollback trigger any financial/tenant invariant failure, health failure, error rate >1% or >2x baseline sustained 5min, p95 regression >30% sustained 10min, failed synthetic golden transaction. These are engineering defaults for review, not universal SLOs. Migration unsafe for rollback => stop rollout/forward-fix, never blind restore. No real money in synthetic tests.
