# M0 trusted CI boundary

Status: **implemented on the bootstrap branch, not yet installed on protected `main`**. ADR-032 records this engineering choice. The current default branch is the README-only SHA `138bdb78530403bac8407738c05fe033514a7838`; no default-branch verifier can run until the bootstrap PR is independently approved and merged. A green candidate job before that merge is useful test evidence, not trusted-gate proof or M0.0 acceptance.

## Threat and boundary

A `pull_request` workflow is taken from the proposed merge commit. The PR can edit the workflow, its job name, its steps and its artifact. The existing `engineering-baseline` required context is sourced from the GitHub Actions app, which does not identify one workflow path. The original design therefore let a PR submit a superficially successful required job. The test loader also imported PR-supplied tests into the same Python process that later ran security checks. Both paths are treated as hostile.

The candidate workflow `.github/workflows/engineering-baseline.yml` has `contents: read`, checks out the exact PR head without persisted credentials, and passes no secrets. It runs the base `baseline.py` where available and labels the README-only first import `bootstrap-exception`. Candidate tests run inside a Python image pinned by digest, with no network, no inherited environment or token, read-only checkout and root filesystem, non-root user, no Linux capabilities, process/CPU/memory/output limits and a 90-second wall limit. The host evaluator never imports a candidate test. Missing Docker, an image pull failure, timeout or a failing test fails closed. `bootstrap/regression_tests/test_unit_boundary.py` retains the old exploit fixture and confirms the new boundary with a real container.

The second workflow `.github/workflows/engineering-trusted-gate.yml` uses `workflow_run` and must exist on default `main`. It checks out only that default-branch policy and reads the candidate run metadata and artifact as untrusted data. Its script verifies the live GitHub run, PR number, exact base/head/policy SHA, unchanged workflow and gate bytes, job result, artifact name and bounded contents before reporting a result for the exact head. It does **not** check out or execute PR code. It has no production credential or repository secret; its only write scope is the commit status needed to report the decision. An artifact with `PASS` text cannot replace the GitHub run and provenance checks.

A candidate that changes `.github/workflows/**`, `bootstrap/baseline.py` or `bootstrap/trusted_gate.py` after the initial import is rejected by base policy and by the trusted verifier. The first import from a README-only base is an explicit seed exception and remains dependent on an independent human GitHub review and merge. The candidate result and two AI reviews do not grant that authority.

## Server-side enforcement and bootstrap sequence

`main` currently requires `engineering-baseline` from the GitHub Actions app plus one non-author approval. That check is a candidate check and is **not** an unforgeable trusted check for PR #1. GitHub documents that a `workflow_run` job runs on the default branch and that `pull_request_target` checks do not themselves satisfy a PR-head required status. The trusted workflow therefore posts a head commit status and the branch rule must require the exact posted context `engineering-trusted-gate-status` after the seed merge. To prevent another PR workflow using the same GitHub Actions app from spoofing this context, a server-side restricted-path rule for `.github/workflows/**` and the trusted gate files must also be activated if this repository plan supports it, or the context must be produced by an independent GitHub App and pinned to that App ID. Neither is claimed active before an API readback and a live workflow-edit attack test. Do not weaken the current PR/review protection to seed the gate.

The exact activation order is: independent person reviews and merges PR #1 under current protection; verify `main` SHA; run the default-branch trusted verifier on a new Shadow PR; configure and read back the required trusted status and protected paths; inject a workflow-spoof attempt and observe a hard block; freeze and rerun final evidence. Until then, M0.0 is PENDING. GitHub's planned public-repository default policy for `pull_request_target` does not affect this `workflow_run` design, but a change in GitHub's event policy still requires revalidation.

## Evidence and limits

A valid ENG-RUN names the exact base/head/policy SHA, candidate and trusted run IDs, downloaded artifact digests, writer and independent read-only reviewer identities with real effective provider/model disclosure, hard checks, time/repair/cost caps and kill switch state. `engrun.py` must query GitHub for both runs; a PR-authored JSON file cannot certify itself. A failed hard check, absent trusted run, stale SHA, unverified model identity or open P0/P1 is FAIL/PENDING regardless of AI votes. No automated merge, deployment, product dependency install or V1.0 feature is enabled here.
