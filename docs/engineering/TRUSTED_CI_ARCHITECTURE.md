# M0 trusted CI boundary

Status as observed 2026-09-29: **the trusted workflow is installed on protected `main`, but its first live Shadow run failed closed; M0.0 remains PENDING**. ADR-034 is the current accepted boundary; ADR-035 is a proposed provenance repair, not yet an accepted supersession. PR #1 was independently approved at head `b8853c7a59a34eaca8bcaa5a153d949f0b275069` and merged as `9af7ac8a4b8cd7ea96c27a2eb5f4c69c92d33659`. Repository event policy 5892 reads back active, and strict `main` protection requires `engineering-trusted-gate-status` from GitHub Actions App ID 15368. These configuration facts do not establish a working trusted gate: protected-main Shadow run `36525390832` failed at the verifier's incorrect run-SHA assumption.

## Threat and boundary

A `pull_request` workflow is taken from the proposed merge commit. The PR can edit the workflow, its job name, its steps and its artifact. The existing `engineering-baseline` required context is sourced from the GitHub Actions app, which does not identify one workflow path. The original design therefore let a PR submit a superficially successful required job. The test loader also imported PR-supplied tests into the same Python process that later ran security checks. Both paths are treated as hostile.

The candidate workflow `.github/workflows/engineering-baseline.yml` has `contents: read`, checks out the exact PR head without persisted credentials, and passes no secrets. It runs the base `baseline.py` where available and labels the README-only first import `bootstrap-exception`. Candidate tests run inside a Python image pinned by digest, with no network, no inherited environment or token, read-only checkout and root filesystem, non-root user, no Linux capabilities, process/CPU/memory/output limits and a 90-second wall limit. The host evaluator never imports a candidate test. Missing Docker, an image pull failure, timeout or a failing test fails closed. `bootstrap/regression_tests/test_unit_boundary.py` retains the old exploit fixture and confirms the new boundary with a real container.

The second workflow `.github/workflows/engineering-trusted-gate.yml` uses `pull_request_target` and must exist on default `main`. It has two separate jobs. `candidate-check` receives a read-only token, checks out trusted main policy and the exact candidate head into separate directories, and executes only trusted `baseline.py` on the host. PR-supplied tests execute solely in the restricted Docker container. `trusted-gate` has status-write permission but checks out **only main**. It verifies the live PR, exact base/head/policy SHA, unchanged workflow and gate bytes, completed candidate job and bounded artifact bytes/digest. It preserves its own report before posting a decision to the exact PR head. A missing/failed upload prevents a success status. It never checks out or executes PR code. No production credential or repository secret is passed to either job.

A candidate that changes `.github/workflows/**`, `bootstrap/baseline.py` or `bootstrap/trusted_gate.py` after the initial import is rejected by base policy and by the trusted verifier. The first import from a README-only base is an explicit seed exception and remains dependent on an independent human GitHub review and merge. The candidate result and two AI reviews do not grant that authority.

Adversarial review found that merely protecting existing test files was insufficient: a newly added test or importable module could monkeypatch `unittest` inside the candidate container and mask an old test failure. ADR-034 narrows post-seed M0 changes to Markdown under `docs/`, the named state/readme files, and text under `samples/`. All bootstrap code, tests, workflows and other executable/importable files are frozen; a policy evolution needs a separate reviewed trust migration. The disposable `test_000_poison.py` regression first reproduced the masked failure, then the post-seed path gate rejected the addition. The candidate container remains necessary to keep untrusted code away from the host evaluator.

Another adversarial review found that a PR-body edit can change traceability without changing the required status SHA. The hard traceability check now reads the exact head commit message, which changes only with a new SHA. The PR body is useful for human review but is not a deterministic hard-gate input; `edited` is not a required workflow trigger. The regression first showed an invalid body failing despite an unchanged valid head message, then passed after the SHA-bound repair. Trace markers are a minimum mechanical check, not proof of the semantic REQ/ADR mapping, which the independent reviewers still examine.

## Server-side enforcement and bootstrap sequence

`main` now requires the posted exact-head context `engineering-trusted-gate-status` from GitHub Actions App ID 15368, with strict checks, one non-author approval, stale-review dismissal, last-push approval and admin enforcement. Force pushes and deletion are disabled. Repository Actions event policy **5892** is active for `~ALL` workflow paths and permits only `pull_request_target`. This prevents PR-owned `pull_request`, `push`, `workflow_dispatch` and `workflow_run` definitions from producing a same-App substitute check; `pull_request_target` loads workflow code from protected `main`. These settings were read back after the seed merge. The policy also suppresses other Actions events during M0; expanding it needs a reviewed ADR and attack proof.

The native PR-target job check **does not use the base SHA in the observed run**. In Shadow run `36525390832`, GitHub's run `head_sha`, both job `head_sha` fields and artifact `workflow_run.head_sha` identify candidate `bbe16a0069d37867eed41bc7a137c5ab17721334`; runner `GITHUB_SHA`/`POLICY_SHA` is protected-main `9af7ac8a4b8cd7ea96c27a2eb5f4c69c92d33659`. The run uses event `pull_request_target` and workflow path `.github/workflows/engineering-trusted-gate.yml`. The current verifier incorrectly equates API run `head_sha` with the policy SHA, so its `trusted-gate` job rejected this legitimate run with `trusted run is not the protected-main workflow` and the required status did not pass. The candidate job succeeded, but its green check cannot substitute for the failed trusted status. An artifact's candidate `head_sha` likewise does not by itself prove where the policy code came from.

The proposed ADR-035 binding keeps those identities separate. The PR head must match the live PR, event PR, run/job/check candidate SHA, artifact origin and exact candidate report. The policy SHA must match the protected-main event context, trusted checkout, live `main` ref, PR base and immutable policy bytes. The workflow ID/path, `pull_request_target` event, run ID/attempt, job IDs, artifact digest and active event policy must also agree. Only a verified result may post the required status to the current exact PR head. Dropping a mismatched SHA check or treating a candidate artifact as policy proof would weaken this boundary.

The seed approval/merge, `main` SHA readback, policy 5892 activation and strict required-status readback have occurred. The next live step, Shadow PR #2, **failed closed** as described above. A corrected verifier is a trust-code change. ADR-034 freezes trust code after the seed, so the existing trusted gate must reject such a migration PR. Its required status and branch protection must remain effective; a normal PR cannot be merged merely because its candidate tests or AI reviewers pass. The migration merge procedure therefore needs a separate explicit human decision and independently reviewed, auditable protection plan. This document grants no admin bypass, temporary relaxation, direct push, self-approval or self-merge. Until that path is authorized and completed, leave the operational P1 open and M0.0 PENDING.

After an approved protected migration, read back the exact new `main` policy SHA, policy 5892 and required status; rerun Shadow PR #2 on that SHA; run a real workflow/gate-spoof PR and observe that PR-controlled workflows cannot execute, the trusted gate rejects the attempted edit and merge stays blocked; obtain independent exact-SHA reviews and a final ENG-RUN from the verified live artifacts. Do not infer Shadow PASS or spoof resistance from the current failed run, or start M0.2 before M0.0 has a real PASS.

## Evidence and limits

A valid ENG-RUN names exact base/head/policy SHA, the protected-main run/attempt/job and artifact IDs/digests, writer and independent read-only reviewer identities with real effective provider/model disclosure, hard checks, time/repair/cost caps and kill switch state. `engrun.py` queries GitHub for the trusted run, active event policy, required check and exact-head status; a PR-authored JSON file cannot certify itself. Its reviewer gate rejects open P0/P1 even when an AI verdict says PASS. A failed hard check, absent trusted run, stale SHA, inactive policy, missing artifact or open P0/P1 is FAIL/PENDING. No automated merge, deployment, product dependency install or V1.0 feature is enabled here.

An ENG-RUN PASS would describe the automated engineering evidence for its target SHA. The CLI does not decide that a GitHub person approved or merged PR #1; those steps now have separate live GitHub evidence. M0.0 acceptance still requires a working protected-main gate, successful live Shadow and spoof-attack proof, exact-SHA reviews and no open P0/P1. GitHub branch protection is the merge authority. An automated PASS alone must never be presented as M0.0 PASS.

ENG-RUN also requires each local reviewer report's exact bytes to appear as the **latest final answer** in a distinct Codex subagent session outside the PR checkout, with matching session ID, agent path, parent task, effective provider/model, target SHA and findings. A writer-created report with a recalculated hash, or an old PASS superseded by a later FAIL, cannot meet that check. Local session files on this WSL host are unsigned and host-writable, so this is **observed consistency and PR isolation evidence, not a cryptographic reviewer signature or enforced read-only proof**. The human non-author GitHub review remains mandatory. The ENG-RUN CLI fails closed when these session records are unavailable.

The scoped writer must identify two ordered successful command events in the parent Codex session outside the PR checkout: a simple `git -c core.abbrev=40 commit -F /tmp/<message>` or `git -c core.abbrev=40 commit --amend --no-edit` that prints the exact branch and complete target SHA, then exactly `git rev-parse HEAD` returning the same complete SHA. The entire shell command must match one of these audited forms. A prefix-only parser was exploitable with a failed background commit followed by a forged `printf` success line; the pre-fix test reproduced that acceptance before the exact-command repair. Both events must use this checkout, and their recorded timestamps must be inside the at-most-one-hour writer lease. The effective model is taken from the active turn when the commit occurred, so a later model switch cannot relabel the write. GitHub's live PR plus exact head commit author/committer login is checked separately. An unrelated old root session with the correct model was also accepted before this repair; its pre-fix regression failed and the repaired 28-test suite passed in a restricted container. These local records are unsigned and host-writable, so they show observed coordination rather than cryptographic authorship or an OS-enforced one-writer lock. They do not turn the failed Shadow run into a trusted-main PASS.
