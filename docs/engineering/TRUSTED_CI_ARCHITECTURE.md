# M0 trusted CI boundary

Status: **implemented on the bootstrap branch, not yet installed on protected `main`**. ADR-034 supersedes ADR-033 after adversarial review; ADR-033 had superseded the earlier workflow-run proposal ADR-032. The current default branch is the README-only SHA `138bdb78530403bac8407738c05fe033514a7838`; no default-branch verifier can run until the bootstrap PR is independently approved and merged. A green PR-owned candidate job before that merge is test evidence, not trusted-gate proof or M0.0 acceptance.

## Threat and boundary

A `pull_request` workflow is taken from the proposed merge commit. The PR can edit the workflow, its job name, its steps and its artifact. The existing `engineering-baseline` required context is sourced from the GitHub Actions app, which does not identify one workflow path. The original design therefore let a PR submit a superficially successful required job. The test loader also imported PR-supplied tests into the same Python process that later ran security checks. Both paths are treated as hostile.

The candidate workflow `.github/workflows/engineering-baseline.yml` has `contents: read`, checks out the exact PR head without persisted credentials, and passes no secrets. It runs the base `baseline.py` where available and labels the README-only first import `bootstrap-exception`. Candidate tests run inside a Python image pinned by digest, with no network, no inherited environment or token, read-only checkout and root filesystem, non-root user, no Linux capabilities, process/CPU/memory/output limits and a 90-second wall limit. The host evaluator never imports a candidate test. Missing Docker, an image pull failure, timeout or a failing test fails closed. `bootstrap/regression_tests/test_unit_boundary.py` retains the old exploit fixture and confirms the new boundary with a real container.

The second workflow `.github/workflows/engineering-trusted-gate.yml` uses `pull_request_target` and must exist on default `main`. It has two separate jobs. `candidate-check` receives a read-only token, checks out trusted main policy and the exact candidate head into separate directories, and executes only trusted `baseline.py` on the host. PR-supplied tests execute solely in the restricted Docker container. `trusted-gate` has status-write permission but checks out **only main**. It verifies the live PR, exact base/head/policy SHA, unchanged workflow and gate bytes, completed candidate job and bounded artifact bytes/digest. It preserves its own report before posting a decision to the exact PR head. A missing/failed upload prevents a success status. It never checks out or executes PR code. No production credential or repository secret is passed to either job.

A candidate that changes `.github/workflows/**`, `bootstrap/baseline.py` or `bootstrap/trusted_gate.py` after the initial import is rejected by base policy and by the trusted verifier. The first import from a README-only base is an explicit seed exception and remains dependent on an independent human GitHub review and merge. The candidate result and two AI reviews do not grant that authority.

Adversarial review found that merely protecting existing test files was insufficient: a newly added test or importable module could monkeypatch `unittest` inside the candidate container and mask an old test failure. ADR-034 narrows post-seed M0 changes to Markdown under `docs/`, the named state/readme files, and text under `samples/`. All bootstrap code, tests, workflows and other executable/importable files are frozen; a policy evolution needs a separate reviewed trust migration. The disposable `test_000_poison.py` regression first reproduced the masked failure, then the post-seed path gate rejected the addition. The candidate container remains necessary to keep untrusted code away from the host evaluator.

Another adversarial review found that a PR-body edit can change traceability without changing the required status SHA. The hard traceability check now reads the exact head commit message, which changes only with a new SHA. The PR body is useful for human review but is not a deterministic hard-gate input; `edited` is not a required workflow trigger. The regression first showed an invalid body failing despite an unchanged valid head message, then passed after the SHA-bound repair. Trace markers are a minimum mechanical check, not proof of the semantic REQ/ADR mapping, which the independent reviewers still examine.

## Server-side enforcement and bootstrap sequence

`main` currently requires `engineering-baseline` from GitHub Actions App ID 15368 plus one non-author approval. That is a PR-controlled candidate check for PR #1. GitHub required-check matching does not bind a workflow path; another PR workflow can request an Actions token and post a same-App context. The staged repository Actions event policy **5892** targets `~ALL` workflow paths and allows only `pull_request_target`, but is currently **disabled**. Once activated, PR-controlled `pull_request`, `push`, `workflow_dispatch` and `workflow_run` definitions cannot execute, while `pull_request_target` loads only protected-main workflow code. Then branch protection must require the exact posted head context `engineering-trusted-gate-status` from App ID 15368. The native PR-target job check uses the base SHA, so the exact-head commit status is the merge gate. This server-side restriction is necessary for the App source to mean trusted code. It also intentionally suppresses other Actions events during M0; a later expansion requires a reviewed ADR and attack proof.

The activation order is: a real independent person reviews and merges PR #1 under current protection; verify `main` SHA; activate policy 5892 and read it back; replace the required candidate context with `engineering-trusted-gate-status` (App ID 15368) and read back strict protection; retarget/re-run Shadow PR #2 against main; run a real PR that edits/adds a spoof workflow and observe that its PR-controlled workflow cannot run, the trusted gate fails and merge remains blocked; only then produce final exact-SHA ENG-RUN. No protection bypass is allowed for the seed. The public-repository default block for `pull_request_target` planned by GitHub makes the explicit active event policy operationally necessary. Until each readback and live attack succeeds, M0.0 is PENDING.

## Evidence and limits

A valid ENG-RUN names exact base/head/policy SHA, the protected-main run/attempt/job and artifact IDs/digests, writer and independent read-only reviewer identities with real effective provider/model disclosure, hard checks, time/repair/cost caps and kill switch state. `engrun.py` queries GitHub for the trusted run, active event policy, required check and exact-head status; a PR-authored JSON file cannot certify itself. Its reviewer gate rejects open P0/P1 even when an AI verdict says PASS. A failed hard check, absent trusted run, stale SHA, inactive policy, missing artifact or open P0/P1 is FAIL/PENDING. No automated merge, deployment, product dependency install or V1.0 feature is enabled here.

An ENG-RUN PASS would describe the automated engineering evidence for its target SHA. The CLI does not decide that a GitHub person approved or merged PR #1; M0.0 acceptance separately requires the observed non-author approval and protected merge, followed by policy/status activation and live Shadow/spoof tests. GitHub branch protection is the merge authority. An automated PASS alone must never be presented as M0.0 PASS.

ENG-RUN also requires each local reviewer report's exact bytes to appear as the **latest final answer** in a distinct Codex subagent session outside the PR checkout, with matching session ID, agent path, parent task, effective provider/model, target SHA and findings. A writer-created report with a recalculated hash, or an old PASS superseded by a later FAIL, cannot meet that check. Local session files on this WSL host are unsigned and host-writable, so this is **observed consistency and PR isolation evidence, not a cryptographic reviewer signature or enforced read-only proof**. The human non-author GitHub review remains mandatory. The ENG-RUN CLI fails closed when these session records are unavailable.

The scoped writer must identify two ordered successful command events in the parent Codex session outside the PR checkout: a simple `git -c core.abbrev=40 commit -F /tmp/<message>` or `git -c core.abbrev=40 commit --amend --no-edit` that prints the exact branch and complete target SHA, then exactly `git rev-parse HEAD` returning the same complete SHA. The entire shell command must match one of these audited forms. A prefix-only parser was exploitable with a failed background commit followed by a forged `printf` success line; the pre-fix test reproduced that acceptance before the exact-command repair. Both events must use this checkout, and their recorded timestamps must be inside the at-most-one-hour writer lease. The effective model is taken from the active turn when the commit occurred, so a later model switch cannot relabel the write. GitHub's live PR plus exact head commit author/committer login is checked separately. An unrelated old root session with the correct model was also accepted before this repair; its pre-fix regression failed and the repaired 28-test suite passed in a restricted container. These local records are unsigned and host-writable, so they show observed coordination rather than cryptographic authorship or an OS-enforced one-writer lock. They do not turn the unmerged seed into a trusted-main run.
